# ChessTube Analyzer Coding Standards

This document is the repository-wide coding standard for ChessTube Analyzer. It
applies to production code, tests, tooling, and documentation. Agents and
contributors must read and follow it before making changes. If an existing
implementation conflicts with this document, preserve behavior first and make
the smallest compatible improvement unless the task explicitly asks for a
broader migration.

## General principles

- Keep changes focused. Do not reformat or rewrite unrelated files while
  implementing a feature or fix.
- Prefer simple, explicit code over clever abstractions. Keep functions and
  classes focused on one responsibility.
- Preserve the existing public API unless a change is required by the task.
  When an API must change, update all callers and relevant documentation in the
  same change.
- Explain non-obvious algorithms, thresholds, invariants, and ownership rules
  with comments. Comments should explain why, not restate what the code says.
- Do not hide failures, silently discard data, or add broad catch-all handling
  that makes a faulty extraction appear successful.

## C++ and project structure

- Use C++20 as configured by the top-level `CMakeLists.txt`. Do not introduce a
  newer language requirement without updating the build and documenting the
  compatibility impact.
- Keep public headers in `include/` and implementations in `src/`. Tests belong
  in `tests/`. Follow the existing `namespace cta { ... }` convention for
  project code.
- Use `#pragma once` in project headers. Include the matching project header
  first in a `.cpp` file, followed by project headers, third-party headers, and
  standard-library headers. Keep include lists minimal and use forward
  declarations when they avoid unnecessary compile-time coupling.
- Use `PascalCase` for types, `camelCase` for functions and parameters, and
  `snake_case_` for private data members, matching the established codebase.
  Use descriptive names rather than abbreviations that require local context.
- Prefer `const`, references, `std::string_view`, and value types where they
  make ownership and mutation clear. Avoid unnecessary copies, but do not
  sacrifice clarity for speculative optimization.
- Use RAII and standard ownership types. A raw pointer must be non-owning and
  its lifetime must be clear; owning raw pointers and manual `new`/`delete` are
  not permitted in new code.
- Use `enum class`, scoped constants, and typed interfaces instead of unrelated
  magic numbers or stringly-typed state. Name domain-specific thresholds and
  document their units or source.
- Keep platform-specific code behind the existing platform checks and utility
  boundaries. Do not spread Windows-only assumptions through platform-neutral
  modules.

## Architecture and correctness

- Treat the chronological verification reducer as the correctness boundary for
  extracted chess state. Mapper work may propose observations, but it must not
  independently mutate the authoritative game state.
- Production extraction logic must remain fixture-independent. It must not
  branch on a test label, video filename, asset path, expected move list, clock
  value, or another identifier unique to one fixture.
- Keep all accepted moves legal and validate them using reusable visual/state
  evidence. If a fixture exposes a detector gap, add diagnostics or a general
  detector improvement instead of an expected-output override.
- Preserve provenance for timestamps, clocks, reverts, and variations. Do not
  turn inherited or missing observations into fabricated direct observations.
- Make cancellation, thread-safety, and ordering guarantees explicit when
  adding asynchronous work. Avoid shared mutable state; protect unavoidable
  shared state with the narrowest appropriate synchronization.
- Keep extraction, verification, engine analysis, opening lookup, rendering,
  and output generation separated at their existing module boundaries. New
  cross-module behavior should use a clear data contract rather than reaching
  into another module's private state.

## Qt UI and theme rules

- Every UI element—including buttons, labels, input fields, toggles, combo
  boxes, group boxes, and dialogs—must have a useful mouseover hint via
  `setToolTip()`.
- All colors and widget styling must come from `ThemeManager`. Do not add
  hardcoded colors, custom per-widget stylesheets, or direct style overrides.
  Custom-painted widgets must obtain current colors from
  `ThemeManager::instance().colors()` while painting.
- When adding a theme-dependent visual, add its color to `ThemeColors` and
  define it for both light and dark themes. Standard widgets should rely on the
  global stylesheet generated by `ThemeManager`.
- Apply theme changes through the existing `MainWindow::applyTheme()` flow so
  the complete UI remains consistent.

## Errors, logging, and external resources

- Fail fast for unrecoverable initialization or missing required resources,
  using the project's established exception and logging conventions.
- Include actionable context in errors: the operation, relevant path or
  resource, and the reason when available. Never log secrets such as API tokens.
- Use the existing safe-path, logging, FFmpeg, and network helper boundaries
  instead of duplicating platform-specific resource handling.
- Keep cache and generated-output behavior explicit. Do not write intermediate
  files into the repository unless the task specifically requires a fixture or
  documentation asset.

## Tests and verification

- Add or update a focused test when behavior changes, especially for move
  legality, reverts, clocks, timestamps, variations, UI detectors, and output
  serialization.
- Tests may identify fixtures and assert known expected results. Production code
  may not use those test-only identifiers to select behavior.
- Prefer deterministic tests and test the smallest relevant module before an
  integration run. Include edge cases such as empty input, cancellation,
  malformed resources, promotions, reverts, missing clocks, and terminal chess
  positions when applicable.
- Before handoff, run the narrowest relevant test/build command and report what
  was run and any environment-limited checks that could not be run. Do not
  claim a test passed when it was not executed.

## CMake, dependencies, and generated files

- Add source files to the appropriate CMake target and keep build options
  consistent with the existing presets.
- Respect the documented vcpkg triplet and MSVC runtime pairing. Do not mix
  static and dynamic runtime/dependency configurations casually.
- Prefer existing dependencies and utilities. A new dependency requires a
  clear justification, CMake/vcpkg integration, and documentation of its use.
- Do not commit build trees, binaries, logs, extracted video, caches, or other
  generated artifacts unless they are intentionally versioned project assets.

## Change review checklist

Before considering a change complete, verify:

1. The implementation follows this document and the applicable module rules in
   `agents.md`.
2. New UI elements have tooltips and use the centralized theme system.
3. Production detector logic is generic and does not contain fixture-specific
   branches.
4. Ownership, ordering, cancellation, and error behavior are clear.
5. Relevant tests/builds were run, or the limitation is reported.
6. The diff contains no unrelated formatting, generated files, secrets, or
   accidental behavior changes.
